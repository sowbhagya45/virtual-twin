--- PROJECT AREA 1: AI-POWERED CUSTOMER INSIGHTS PLATFORM ---

One of the most technically complex systems I have built is an enterprise
platform that ingests customer feedback from multiple external sources and
transforms it into actionable, product-centric recommendations for different
business teams. The platform is in production at IBM and serves real business
decisions across product, sales, pricing, and marketing functions.

The system ingests data from seven distinct sources: third-party product review
sites (collected via Selenium web scrapers with bot-detection bypass), a sales
conversation platform (via REST API with a rolling 14-day window), internal
Slack channels (via the Slack API), customer survey exports (via a cloud file
storage integration), and deal loss records from an enterprise DB2 database
(queried over a 12-month window). Each source lands in MongoDB with its
original schema preserved.

The core processing pipeline runs in six stages. First, an LLM (IBM Granite
via WatsonX.ai) extracts structured signals from each document — summary, key
points, topics, and sentiment — and stores them in a unified collection. This
signal extraction approach is a deliberate design choice over raw text chunking:
it improves embedding quality by reducing noise and enables structured
downstream filtering. Second, embedding text is constructed from the extracted
signals and sent to a WatsonX embedding model in batches, producing 384-
dimensional vectors stored in a Milvus vector database. Batch processing reduced
API calls by 80-90% compared to individual document embedding.

Third, dimensionality reduction using UMAP (384 dimensions down to 12) is
followed by HDBSCAN density-based clustering, scoped per product. HDBSCAN was
chosen over k-means because it handles arbitrary cluster shapes, identifies noise
points, and does not require specifying k in advance. Cluster labels are
generated using c-TF-IDF. Fourth, each cluster is scored against four fixed
business team categories with a confidence scoring model. Fifth,
recommendations are generated per team using the LLM, with a hierarchical
summarisation strategy: document-level signals are compressed to cluster-level
summaries, then aggregated to team-level recommendations. This hierarchy
respects context window limits even when thousands of documents are involved.
Evidence — occurrence counts and representative quotes — is preserved throughout.

A key engineering challenge was making the clustering scalable. Full UMAP and
HDBSCAN retraining on all historical data is expensive and O(n²). I implemented
an incremental assignment mode: models are trained once and persisted to disk
using joblib; new data points are assigned to existing clusters using the saved
parametric UMAP transform without retraining. A weekly full refresh catches
model drift. The vector database was migrated from ChromaDB (suitable for
prototyping) to Milvus when the collection grew past the point where ChromaDB
could sustain performance — the migration delivered a 2-4x speedup in semantic
search and enabled multi-tenancy and billion-scale capacity.

The platform is deployed on IBM Cloud, containerised with Docker, and run via
a scheduled job framework (APScheduler). The API layer is built in FastAPI with
Motor for async MongoDB access. The frontend is a React dashboard with Redux
state management, giving different business teams role-specific views of
recommendations. PII anonymisation using Presidio and SpaCy NER runs as a
preprocessing step before any data is processed by the LLM.

The tech stack for this platform includes: Python 3.12+, FastAPI, Motor,
IBM WatsonX.ai (Granite models and embedding models), MongoDB, Milvus
(pymilvus 3.0+), Redis, UMAP, HDBSCAN, scikit-learn, pandas, numpy, scipy,
joblib, Selenium, undetected-chromedriver, BeautifulSoup, APScheduler,
IBM Cloud Object Storage, Docker, LangSmith, Presidio, SpaCy, React, Redux,
Vite, Poetry.

--- PROJECT AREA 2: MULTI-AGENT AI ASSISTANT ---

I designed and built the core multi-agent architecture for an enterprise AI
assistant used by IBM sales teams. The system uses a LangGraph supervisor
pattern: a central supervisor agent classifies the intent of each incoming
query and routes it to one of several specialised sub-agents, each built
using the ReAct reasoning pattern.

The primary sub-agents handle product intelligence queries (fetching and
synthesising metadata from multiple internal knowledge sources), presentation
generation (dynamically creating PowerPoint slides from retrieved content),
and language translation. Each sub-agent has access to tools defined as
Python functions with Pydantic schemas; tool calling is handled natively by
the WatsonX-LangGraph integration.

The system uses a multi-model strategy: a larger Granite model handles
complex reasoning tasks (the planner), a smaller, faster Granite variant
handles cost-sensitive classification and fallback, and an external model
handles translation. Model selection is configurable via environment variables,
which allows cost-quality tradeoffs to be adjusted without code changes.

A metadata builder pattern abstracts the differences between knowledge sources:
each source has its own implementation of a common abstract base class, and
a factory selects the right builder at runtime. Prompt templates are managed
via a service that loads Jinja2 files dynamically, enabling prompt iteration
without redeployment.

Observability is built in from the start: every LLM call is traced with model,
prompt, token count, latency, and tool invocations using LangFuse. Request ID
middleware (UUID) enables end-to-end distributed tracing across agent hops.
Resilience is handled via maximum recursion limits on the LangGraph, explicit
END conditions for each sub-agent, error-catching tool wrappers that return
structured error signals rather than raising exceptions, and fallback to a
smaller model on primary model failure.

The documented business impact of this system includes significant annual cost
savings, a reduction in review cycle time from weeks to days, high classification
accuracy, and a large number of risk findings surfaced for downstream governance
processes.

Tech stack: FastAPI, LangGraph, IBM WatsonX.ai (Granite models), OpenAI models
(translation), Elasticsearch, PostgreSQL, Box SDK, Tavily Search API, LangFuse,
Jinja2, Pydantic.

--- PROJECT AREA 3: ENTERPRISE PORTAL WITH AI CAPABILITIES ---

I contributed to a large multi-service enterprise portal that combines contract
document processing, a dynamic API generation layer, an AI-powered chatbot,
Jira integration, and automated translation services. Each concern is a
separate microservice, and I worked across several of them.

The contract processing service handles PDF and CSV ingestion, OCR, and storage
into a vector database for retrieval. The dynamic API service generates REST
CRUD endpoints automatically from MongoDB collection definitions — supporting
aggregation pipeline filters, custom unique key deduplication, and zero-code
API creation from schema definitions.

The most technically interesting component is a Jira integration service
implemented as a Model Context Protocol (MCP) server — one of the earlier MCP
implementations in the IBM ecosystem. It exposes eleven tools: semantic natural
language search over Jira issues, AI-generated issue summaries, board and sprint
management, issue assignment, and vector database statistics. The server
deploys in stdio mode locally and via Server-Sent Events (SSE) in production,
and integrates with IBM WatsonX Orchestrate as an agent tool.

The translation service connects to GitHub webhooks to detect new or changed
i18n strings, routes them to a professional translation API (supporting French,
Japanese, and other languages), and posts success or failure notifications to
Slack. This eliminated manual translation bottlenecks in the UI release process.

Key engineering challenges solved include: PostgreSQL connection pool exhaustion
under concurrent load (root cause was a global session shared across threads;
fix was per-request session injection with try/finally cleanup via FastAPI
Depends()), and LLM API instability (a cloud-side Redis failure caused cascading
500 errors; fixed with exponential backoff retry at 1s, 2s, and 4s intervals).

Tech stack: FastAPI, SQLAlchemy (PostgreSQL), Motor (MongoDB), Milvus, JWT,
OAuth2, IBM WatsonX.ai, Model Context Protocol (MCP), Server-Sent Events,

--- PROJECT AREA 4: PERSONAL PROJECT — AI VIRTUAL TWIN ---

As a personal project, I built an agentic AI virtual twin of myself using
LangGraph, Google Gemini, and Streamlit. It answers questions about my skills
and experience using RAG over my resume, books meetings via a multi-step
scheduler agent, notifies me via email when someone asks something outside
the knowledge base, and handles small talk with a personalised tone.

The agent graph has a supervisor (Gemini 2.0 Flash for low-latency routing)
and four sub-agents: a RAG agent (Gemini 1.5 Pro for deep answers, reading

a scheduler agent (multi-turn booking flow with state persistence), a notifier
agent (SendGrid email for out-of-scope questions), and a chitchat agent.

(langgraph-checkpoint-sqlite) works on Streamlit Community Cloud's ephemeral
filesystem without any managed database. ChromaDB rebuilds from the resume on
cold start in about 30 seconds. The knowledge base is updated by editing the
FAQ string in the ingest script and re-running it — no redeployment needed.

Tech stack: LangGraph 0.2+, Gemini 2.0 Flash, Gemini 1.5 Pro, Gemini
text-embedding-004, ChromaDB, SQLite checkpointer, Streamlit, SendGrid,

5. HOW I APPROACH TECHNICAL PROBLEMS
================================================================================

When designing a system I start with the data flow, not the technology choice.
I ask: what data comes in, what transformation happens, what comes out, and
where can this go wrong? I identify failure modes early — before writing code —
and design graceful degradation into the architecture from the start.

I prefer proven, well-understood technology for well-understood problems. I
reach for MongoDB when I genuinely need schema flexibility, Milvus when I
genuinely need billion-scale vector search, and a simple SQLite file when
neither is needed. Every technology choice should have a clear rationale. I
have learned through production experience that premature architectural
sophistication is as dangerous as under-engineering.

Observability is not an afterthought. I instrument systems with structured
logging, per-request tracing IDs, and LLM call tracing before I ship a feature.
The ability to replay a conversation or pipeline run from logs has saved me
many hours of debugging. For AI systems specifically, I track retrieval quality,
faithfulness metrics, and classification accuracy in production — not just
during evaluation.

For AI systems reliability means: retries with exponential backoff for
transient failures, circuit breakers for sustained failures, graceful degraded
responses when upstream dependencies are down, and fallback models when
the primary model is unavailable. I have hit each of these failure modes in
production and have the muscle memory to build for them automatically.

When I debug a malfunctioning RAG pipeline, I first isolate whether it is a
retrieval problem or a generation problem by inspecting the retrieved chunks
manually. If retrieval is the issue I check embedding quality (cosine
similarity between query and expected document), chunk boundaries, and metadata
filters. If generation is the issue I inspect the prompt sent to the model,
try forcing the model to ground in context, and check whether the answer
requires multi-hop reasoning that a single retrieval step cannot satisfy.
LangSmith or LangFuse tracing gives me the full chain — exact prompts sent,
exact chunks retrieved, model output — which makes this diagnostic fast.

When a FastAPI service works locally but fails under load in Kubernetes I
follow a checklist: check pod logs for error type, check for connection pool
exhaustion (the most common production failure I have seen), profile the
async event loop for blocking tasks, check memory limits for ML model
footprints, check for shared mutable state under concurrency, and replicate
the load pattern locally with locust or k6.

6. DESIGN PATTERNS AND ARCHITECTURAL PREFERENCES
================================================================================

I use a consistent set of design patterns across my projects. Dependency
injection via FastAPI's Depends() keeps services testable and avoids global
state. The factory pattern abstracts differences between data sources or model
providers behind a common interface — allowing new sources to be added without
modifying calling code. The template method pattern manages prompt templates,
loading Jinja2 files dynamically so prompts can be updated without
redeployment. The strategy pattern makes vector stores, translation backends,
and embedding models pluggable. The supervisor pattern structures multi-agent
systems with a clear routing layer and specialised sub-agents, each with a
single responsibility. Repository patterns isolate database access from
business logic.

For multi-tenant AI systems I follow strict isolation at every layer: tenant ID
is embedded in every MongoDB document and always included in queries; Milvus
uses partition keys for tenant isolation so cross-partition queries are
architecturally impossible; middleware injects tenant context from JWT claims
automatically so it cannot be omitted by accident; RAG retrieval is scoped by
tenant metadata filter; prompts never include one tenant's data for another
tenant's request.

For multi-agent systems I design to prevent loops and cascading failures: maximum
recursion limits on the graph, explicit END conditions for every sub-agent, error-
catching tool wrappers that return structured error signals rather than
exceptions, and supervisor logic that handles "I couldn't complete this" signals
gracefully. I test agents with deterministic canned responses (temperature=0,
seeded prompts) for unit and integration tests, and use production tracing to
catch non-deterministic regressions.

7. TECHNOLOGY COMPARISONS AND DECISION RATIONALE
================================================================================

VECTOR DATABASES: ChromaDB is my default for local development and
prototyping — zero infrastructure, Python-native, simple API. For production
at enterprise scale (millions of vectors, multi-tenancy, cloud deployment)
I use Milvus. I have migrated systems from ChromaDB to Milvus in production
and the process involves recreating collection schemas, re-embedding documents,
and updating search queries — all straightforward but requiring careful data
validation in shadow mode. Elasticsearch is a strong option when hybrid search
(BM25 combined with dense vectors) is more important than pure semantic search.

LLM PROVIDERS: IBM WatsonX.ai is my production enterprise choice — data
residency guarantees, Granite open weights, IBM support SLAs, and compliance
with IBM's internal AI governance requirements. For personal projects I use
Google Gemini, choosing Flash for latency-sensitive routing and Pro for deep
reasoning tasks. I am familiar with OpenAI APIs and use them for specific
tasks like translation. The key principle is to choose the right model for the
right task within cost and compliance constraints.

AGENT FRAMEWORKS: LangGraph is my choice for complex stateful agent systems.
Its explicit graph model makes state transitions inspectable, debuggable, and
testable in a way that implicit chain-based approaches are not. LangChain LCEL
is suitable for simpler linear pipelines. IBM WatsonX Orchestrate is suitable
when non-technical users need to configure agents via a UI, or when integrating
into IBM's enterprise assistant ecosystem.

CLUSTERING ALGORITHMS: HDBSCAN over k-means for customer feedback clustering.
HDBSCAN does not require specifying k, handles arbitrary cluster shapes,
identifies noise points explicitly (important for feedback data which always
contains irrelevant noise), and produces stable clusters without assumptions
about spherical geometry. k-means remains useful when k is known and clusters
are expected to be roughly equal in size.

PYTHON PACKAGE MANAGERS: Poetry for all production Python projects — lock files,
pyproject.toml as the single source of truth, reproducible builds in Docker.
uv for personal projects where install speed matters more than lock file
stability.

8. SOFT SKILLS AND WORKING STYLE
================================================================================

I make technical disagreements about evidence, not opinion. When I have
advocated for a technology choice (for example, LangGraph over LangChain for
a complex multi-agent system), I build a small prototype of both approaches
and let the comparison speak. This turns a discussion about preferences into
a discussion about concrete tradeoffs. I have found this approach both more
persuasive and more honest — sometimes the prototype proves me wrong.

I cross team and discipline boundaries deliberately. On the customer insights
platform, the initial recommendations I generated were technically correct
but practically unusable — the business teams could not act on them. I ran
discovery sessions with each team to understand their actual questions, then
translated those into team-specific prompt templates. That iteration, which
required sitting in rooms with product managers and sales leads and listening,
is what turned the system from a demo into a tool that drives real decisions.

I treat documentation as a product artifact. I write architecture docs not
because I am asked to, but because systems that are well-documented survive
team changes and stay maintainable. I am also candid in documentation about
what is not working — identifying known technical debt, the reasons it exists,
and a prioritised path to addressing it. This kind of self-awareness in writing
is a form of professional integrity.

I believe production AI requires an engineering discipline that is still not
common in teams that have only worked with AI in research or demo contexts.
Reliability, observability, evaluation, and graceful degradation have to be
designed in from the start, not bolted on after the model "works". I bring this
perspective to any team I join.

9. QUESTIONS I ASK IN INTERVIEWS
================================================================================

I typically ask the following to understand whether a team is genuinely
building AI engineering with rigour:

How does your team balance building on top of LLMs versus building the
infrastructure around them? This reveals whether the work is prompt
engineering or engineering.

What is the biggest reliability challenge in your current AI systems, and
how are you monitoring LLM output quality in production? This tells me whether
they have shipped AI at scale.

How much ownership do engineers have over architecture decisions, and how are
those decisions documented and communicated? This tells me about engineering
culture and autonomy.

What does your evaluation culture look like — do you run automated regression
tests on LLM outputs? This tells me whether quality is measured or assumed.

What is the most interesting technical problem you have solved in the last six
months? This tells me whether the work is genuinely challenging.
